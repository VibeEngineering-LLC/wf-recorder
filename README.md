# wf_recorder — рекордер спектрограмм AtomSpectra

Настольная программа (Windows) для непрерывной **записи водопада** (спектрограммы)
с WiFi-шлюза гамма-спектрометра **AtomSpectra** на ESP32-S3.

Основной проект (прошивка шлюза): <https://github.com/VibeEngineering-LLC/atomspectra-waterfall-esp32>

## Что делает

Тонкий pull-клиент поверх HTTP-API шлюза:

- забирает сегменты водопада с платы и сшивает их в **единый файл `.aswf`** (+ `temps.csv`
  с температурами);
- удаляет сегмент на плате **только после `fsync` на диск ПК** — данные не теряются при
  обрыве;
- сегмент опознаётся по **отпечатку содержимого**, не по имени/размеру — переживает перенумерацию
  платы после перезагрузки или перепрошивки;
- контроль целостности формата v4/v5: **CRC32 + порядковые номера сегментов** (#REC-13),
  авто-ротация файла шва при смене формата прошивки (#REC-14) и при **смене калибровки** между
  сегментами (v0.4.0) — файл с чужой калибровкой в шапке не смешивается со старым;
  повреждённая контрольная сумма **не удаляется на плате** — на диске может остаться битая
  копия, но исходник цел, пока не будет забран заново;
  обрыв дозаписи **откатывается** к последней целой границе, а хвост от аварийного завершения
  срезается при следующем запуске;
- окно на `tkinter` (только стандартная библиотека, внешних зависимостей нет): адрес платы,
  файл записи, интервал опроса, Старт/Стоп, счётчики (строк, длительность, температура,
  сегментов на плате) и журнал; `Ctrl+C` — штатная остановка, без трассировки.

## Запуск

Готовый `wf_recorder.exe` — в разделе [Releases](../../releases) (сборка PyInstaller, без
установки Python).

Из исходников:

```bat
:: двойной клик
wf_recorder.bat

:: или напрямую
python wf_recorder_app.py --host http://<IP-платы> --interval 60
```

Требуется Python 3.8+ (только stdlib). Служебные флаги самопроверки: `--autostart`,
`--exit-after N`, `--stitch FILE`.

## Сборка exe

```bat
pip install pyinstaller
pyinstaller wf_recorder.spec
:: результат: dist\wf_recorder.exe
```

## Если в журнале «разрыв в нумерации сегментов»

Программа фиксирует разрыв номеров (например, был `seg_00005`, следующий пришёл `seg_00007`) и
печатает сам факт разрыва с разбором вероятных причин — **но не делает вывод, что данные
потеряны**. Разрыв может значить как реальную потерю (сегмент стёрт до забора), так и то, что
сегмент благополучно остался на плате (например, GET по нему прошёл с таймаутом на стороне
клиента, а команда `ack_delete` из-за этого не отправилась — плата ничего не удаляла). Проверить
факт может только снимок платы: `tools/board_snapshot.py`.

## Если плата перенумеровала сегменты

Номер в имени сегмента (`seg_00042.aswf`) плата восстанавливает при старте **сканом своего
каталога**, а не из энергонезависимой памяти. Значит после перезагрузки на опустевшем каталоге
(всё забрано, потом ребут или перепрошивка) имена начинаются заново — и совпадают с теми, что
клиент уже видел раньше. При постоянном интервале записи совпадает и размер файла.

Клиент это учитывает: сегмент опознаётся по **отпечатку содержимого**, скачивается всегда, а
удаляется на плате только после того, как строки записаны на диск. Совпадение имени само по
себе больше ни на что не влияет.

Версии клиента **до этого исправления** в такой ситуации молча удаляли новые данные, приняв их
за уже забранные. Признак в журнале: сегменты помечены «уже вшит, только ack», а число строк в
файле не растёт. Если видите такую картину — обновите клиент.

### При первом запуске после обновления возможны дубли строк

Клиент опознаёт сегменты по отпечатку содержимого, а записи в `state.json`, сделанные
**прежними** версиями, отпечатка не содержат — только размер. Поэтому сегмент, который был
вшит, но не успел получить подтверждение на плате (обрыв связи ровно в этот момент), при
первом проходе новой версии будет вшит повторно: в файле появятся дублирующиеся строки.

Размен сделан осознанно — повторная строка видна и переживаема, стёртые данные нет. Случай
редкий (нужен обрыв в окне между записью на диск и командой удаления), но если водопад важен
для расчётов, после обновления имеет смысл начать новый файл шва.

### Обходной путь: запись без flash

Если запись во flash не нужна (данные забираются сразу), можно выключить `persist` — тогда
**новые** сегменты не создаются и новых коллизий имён не возникает:

```bat
curl -X POST http://<IP-платы>/api/waterfall/config -d "{\"persist\": false}"
```

Важно: это защищает от появления **новых** коллизий, но не лечит уже накопленное. Сегменты,
записанные раньше, остаются на плате, и их имена по-прежнему могут совпадать с записями в
`state.json`. Пока они не забраны, риск сохраняется.

Плата продолжит копить строки в кольцевом буфере в памяти, откуда их отдаёт
`GET /api/waterfall/export.aswf`. Содержимое кольца **теряется при перезагрузке платы**.

Ёмкость кольца **зависит от платы** — смотрите поле `ring_capacity` в
`GET /api/waterfall/status`. Прошивка запрашивает 256 строк (4 МБ PSRAM), но при нехватке
памяти или фрагментации молча снижает ёмкость вдвое, вплоть до 16 строк, и в лог это не
попадает. При `interval = 180 с` разница существенная: 256 строк — это ≈ 12,8 ч запаса,
16 строк — 48 минут. Рассчитывайте периодичность забора по фактическому значению, а не по
максимальному.

## Состав

| Файл | Назначение |
|---|---|
| `wf_recorder_app.py` | UI-программа (tkinter) поверх pull-клиента |
| `wf_pull_client.py` | логика забора/шва сегментов (Stitcher, CSRF, list/get/delete) |
| `wf_recorder.spec` | спецификация PyInstaller (bundle + `wf_recorder.exe`) |
| `wf_recorder.bat` | лаунчер (UTF-8, `python`/`py -3`) |
| `tools/board_snapshot.py` | снимок состояния платы (список/размеры сегментов) для сверки баланса |
| `tools/balance_check.py` | сверка «что было на плате → что легло в файл шва» по снимкам до/после |
| `test_*.py`, `tools/test_c3_*.py` | 30 регрессионных тестов (`pytest`); каждый фикс проверен на способность краснеть |

## Проверка баланса строк (совместная диагностика с платой)

При подозрении на потерю данных — не полагаться на журнал программы, а сверить снимки платы:

```bat
python tools\board_snapshot.py --host http://<IP-платы> --out before.json
:: ...дать поработать записи некоторое время...
python tools\board_snapshot.py --host http://<IP-платы> --out after.json
python tools\balance_check.py --before before.json --after after.json --seam <файл.aswf>
```

Вердикт трёхзначный: сходится / не сходится / неопределённо (учитывает сегменты, рождённые
внутри окна между снимками). `--light` у `board_snapshot.py` не трогает листинг сегментов —
безопасно запускать во время активной записи.
